CPS-272 · Technical Design Briefing

Self-service onboarding, same trusted verification.

Anyone can create their own account with a verified email or mobile number — then prove their identity in the same KYC module frontliners use today. Exceptions go to humans: approve, redo, or reject.

21tickets, ready for Jira
≈114story points, 8 sprints
10use cases double as UAT
0breaking changes

Portal owns accounts and login. OWA owns capture. KYC back office owns checks plus human review. They meet at exactly one new concept per side: the slug (which tenant), the pending record (no account before code success), and the review case (every exception gets a verdict).

1. Codeprove the contact
2. Accountauto-created
3. Verifysame module
4. Reviewhumans decide
5. AccessKYC-gated apps
Plain-English rule: contact proof is not identity proof. A verified code answers "do you control this number?" — only KYC answers "are you really this person?" Never conflate the two.

01 · Problem

Assisted-only cannot scale

Every account today needs a frontliner with a provisioned staff login. That caps onboarding at frontliner headcount.

  • No public registration — POST /user/register demands an already-logged-in admin.
  • Onboarding app is staff-only — Keycloak login-required on one baked-in realm; anonymous users bounce; one build per tenant.
  • Portal has no register pages and finds tenants by username — impossible for someone with no account yet.
  • Codes are password-reset-only; SMS sending is a logged stub; users carry no KYC state, no history, no attempt tracking.
  • Review is ad hoc — exceptions get manual status patches or delete-and-re-enroll. No approve / redo / reject workflow.
What we keep: verification algorithms, RBAC, one-realm-per-tenant, the assisted flow itself. The design only adds the self-service path.
02 · Solution

Two steps, same modules

Step 1 proves contact control by code before any account exists. Step 2 proves personhood in the same OWA pipeline. KYC status becomes an authorization attribute, backed by immutable history and versioned attempts.

  • Slug-first tenancy — /self-service/{slug}/register names the organisation before any username exists.
  • Same OWA, new self mode — end-user token, runtime tenant, applicant bound to my login; assisted mode untouched.
  • Review queue with teeth — every exception becomes a case; biometric hits wait for a back-office adjudication verdict.
  • Fail-safe defaults — gated apps deny on outage; unknown tenants and taken identifiers get identical replies.

05 · Key flows

Code before account, always

Nothing — no user row, no login-system entry — is created until the code checks out.

sequenceDiagram autonumber actor U as Registrant participant P as Portal participant A as auth-service participant K as Keycloak U->>P: Open tenant link P->>A: Resolve slug to tenant + realm U->>P: Submit contact + password + terms + anti-bot P->>A: Initiate (store pending record, send code) U->>P: Enter code P->>A: Verify code A->>K: Create login only on success A-->>P: Account created, go log in

Verification pipeline — attempt is versioned

sequenceDiagram autonumber actor U as Logged-in user participant O as OWA self mode participant K as KYC back office participant E as Checks (document, national ID, liveness, face search) O->>K: Bootstrap (resume or start attempt N) O->>E: ID capture + inspection + face + liveness E-->>K: Hit? then PENDING adjudication, else results O->>K: Submit attempt N K->>K: Approve, or open review case

Review — adjudication is back-office only

sequenceDiagram autonumber participant J as Adjudicator (back office only) participant R as Reviewer participant K as KYC back office R->>K: Open queue, claim case J->>K: Adjudicate hit (same, different, or inconclusive) R->>K: Approve, redo, or reject K->>K: Update attempt + notify user

Status machine

stateDiagram-v2 [*] --> NOT_STARTED: account created NOT_STARTED --> IN_PROGRESS: start verification IN_PROGRESS --> KYC_VERIFIED: all checks pass IN_PROGRESS --> KYC_REVIEW: exception or hit KYC_REVIEW --> KYC_VERIFIED: approved (or cleared hit) KYC_REVIEW --> REDO_REQUIRED: redo requested KYC_REVIEW --> KYC_REJECTED: rejected REDO_REQUIRED --> IN_PROGRESS: new attempt

A-01 — Self-Service Tenant Resolution by Slug and Portal Bootstrap Critical 5 pts auth-service auth-portal

Story: As a Registrant, I want to open a tenant-specific registration link so that I register under the correct organisation and login realm without needing an existing account.

Build (03 §2, 04 §2.1): resolve + config endpoints (throttled, identical replies for unknown/disabled slugs); slug storage + pilot seeds; portal shell with generic "not available" page.

Acceptance criteria:

  • Valid slug returns tenant, realm, and policy under 300 ms p95 with a resolve audit entry.
  • Unknown versus disabled slugs are indistinguishable in shape and timing.
  • No client secret or internal IDs leak in responses.
  • Burst traffic trips the rate limit with a retry delay.

Story: As a Registrant, I want a one-time passcode sent to my email or mobile so that I can prove I control it before any account exists.

Build (03 §2, 04 §2.3–2.4): initiate (validate, anti-bot, silent existence check, pending + hashed OTP, send code); resend (60 s cooldown, max 5, old code dies); safe status polling.
